No duplicate schema, builder policy or verifier; old review/ledger/installer and v0.1 catalog unchanged.

The trusted local writer explicitly selects a builder policy and repository mapping, TUF bootstrap/cache, ledger scope and namespace. For a new candidate reservation the new callback first recomputes Core's actual Git source membership, strict DSSE statement/policy/subject/build-recipe/source and wheel bytes. Then the actual existing TUF reservation adapter repeats publisher/registry target verification and existing wheel checks. From the refreshed trusted cache verify the builder Ed25519 public key material differs from the root, timestamp, snapshot, targets and selected publisher roles. This is key separation within this fixture profile, not proof of independent organizations, production key custody or builder legal identity.

Only after both checks pass can the existing SQLite writer append its candidate event. The stored authority context binds exact request, registry review, prior TUF context, policy digest, attestation digest, and complete scoped provenance review plus digest. The ledger's receipt commits the exact context bytes; no new editable catalog or duplicate ledger. Retain actual authenticated provenance/policy/source/build artifacts and TUF metadata externally for independent audit; digest alone does not reconstruct evidence. A failed callback does not consume the release key; TUF cache side effects are not rolled back by SQLite. A successful exact retry returns historical receipt, not a fresh trust decision.

No change to historical candidate reservations or automatic enforcement of the new policy on the old path. A candidate reservation does not grant installability, approve a published release, verify SLSA levels, independently prove build execution, complete materials, reproducibility, publisher legal identity or production provenance. The prior TUF review target does not sign the new provenance evidence: production publication needs a **new reviewed versioned admission record** binding all evidence and current authenticated policy plus transactional catalog publication/revocation. Current adapter is only trusted local review code, not an online publisher. No control-operation signer, key rotation, builder isolation, source-fetching, dependency resolver, actual deployment or hardware. Native/OCI/firmware/etc require separate profiles.

CI builds the actual synthetic wheel after creating and materializing a Git commit, verifies real DSSE and TUF signatures using ephemeral keys, and checks persistent candidate ledger/negative cases. No provider import/install, no producer script execution by verifier, no production key material. Existing Registry tests and Calibration source pin preserved.
