## Trust boundaries

- The operator independently provisions TUF root bytes and protected local cache for a named catalog. No root accepted from a submitted proposal. Initial bootstrap is explicit, only when cache is empty; subsequent review reuses cached root and TUF metadata. Do not reset cache on refresh failure, or supply a new root to repair an attack. Cache and real trusted clock are assumptions; no crash-safe local trust-state storage, multi-process locking, compromised-host protection, or clock attestation is implemented. Production manager must own these.
- Use actual python-tuf 7.0.1 Updater (no homegrown signature verifier). Consistent snapshot, explicit SHA-256 lengths/hashes for snapshot/targets/publisher metadata, bounded supplied metadata transport. Ed25519 keys, separate key material for root/timestamp/snapshot/targets and selected publisher. One direct terminating delegation named publisher-<namespace>, paths proposals/<namespace>.*/*; reject overlap, parent shortcut and nested role for the chosen publisher. Registry review is a separate direct top-level targets path reviews/<module_id>/<version>.json. Proposal path is proposals/<module_id>/<version>.json. TUF key/delegation verification is namespace authorization within the supplied trusted catalog, not legal identity or DNS ownership. Thresholds and custody must be separately approved; test keys generated in memory only.
- Review reuses Core artifact inspection and Registry #4 recomputation, legacy-key conflict checks. It verifies the proposal target bytes through the authenticated direct delegation, and separate review target bytes under registry role, then checks proposal/report binding. A signed withdrawal blocks review. A missing/revoked delegation fails closed. No install/enable/start/effect on metadata refresh or verification.
- TUF verifies metadata freshness and rollback under its persistent cache assumptions; it does not freeze a module release key forever. The trusted caller supplies prior exact proposal commitment when present in a retained local review ledger; changed bytes under same key are rejected, including when newly signed. A missing commitment is not proof of global uniqueness. Production durable compare-and-publish, withdrawal/revocation tombstones, explicit historical release selection and concurrency handling remain separate. No ledger implementation in this candidate.
- Artifact profile: actual generated wheel with exact RECORD and embedded manifest/descriptor/CLI declarations; no provider import. TUF signatures authorize the exact candidate proposal and review digest, not a build or source revision. Source retrieval/commit-membership verification, verified SLSA/in-toto builder provenance, license/SBOM, dependencies and semantic validation remain required. An authentic signed malicious wheel is still possible; do not substitute this check for code review or isolation.

## Test protocol

Use ephemeral generated signing keys, synthetic transport over an in-memory metadata map (no HTTP) and real fixture wheel built in CI by Core's test-only producer. Exercise actual TUF client refresh/get_targetinfo and local retained cache across fresh instances. Tests cover tampering, wrong key/scope, shared key material, signed withdrawal, expiry, rollback, missing role/target and re-signed content conflicts. No test metadata or keys are written to the actual catalog; no host changes.

New candidate does not modify Registry v0.1 index, release descriptors, installer, Console, CLI or OS. It is not a production-ready TUF repository server/client deployment or full TUF compliance claim. Native binaries, OCI, firmware, model/data, real builder attestation and release publication transaction require their own profiles.
