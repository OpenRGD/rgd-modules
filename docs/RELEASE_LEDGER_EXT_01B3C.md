## Storage and transaction
One private SQLite database per explicitly provisioned catalog_id and ledger_id. `CandidateLedger.initialize` uses exclusive file creation, not automatic creation on open; incomplete/corrupt/missing state requires recovery. Explicit trusted owner decides storage path, lineage and first boot. Registry v0.1 logical descriptor snapshot is committed using deterministic existing local encoding (not raw repository digest), checked on every transaction; legacy keys cannot be reserved. Changed legacy catalog fails closed pending reviewed migration. No mutation of actual descriptor or index.

A single append-only event table is the candidate history and idempotency index. Unique request_id across ledger and unique key/revision; BEGIN IMMEDIATE serializes independent local writer connections. Request/evidence/proposal/authority-context bytes and receipt commit together, synchronous FULL, rollback journal DELETE, bounded busy timeout. A retry returns original receipt without authorizing again; current view is independently derived. Different request bytes with same ID conflict. Different ID for same reserved content is explicitly rejected, lookup original; changed bytes permanently conflict. Only accepted transactions consume IDs. Withdrawal and revocation append; withdrawn can escalate to revoked; no reinstatement/deletion. Capacity 1024 events, no eviction/compaction. Bounded full replay verifies sequence, exact record links, digest and state machine. Append-only SQL triggers are defense in depth, not protection against a privileged database/file administrator or alternative connection disabling safeguards.

## Authority and trust
`CandidateLedger` is not a public API. Its optional authorizer is trusted in-process owner code; absence denies NEW requests. It receives exact immutable request/proposal/evidence/prior receipt bytes inside the serialized transaction, raises on denial, returns bounded verification-context bytes. Context is opaque evidence, not authenticated just because stored. The supplied local code, caller, directory and database/cache are trusted assumptions. No external side effects (including trust cache updates) are rolled back by SQLite; a failed write may require re-review using existing protected TUF cache. Never reset the cache or ledger to bypass errors. Existing receipt lookup and exact retries are read-only historical views, not current publication/authorization.

`tuf_reservation_authorizer` repeats the actual pinned REG-TRUST-01 TUF + wheel + legacy review path for NEW candidate reservations. The registry writer explicitly selects catalog and ledger scope, protected cache, bootstrap and namespace. The review context stores exact digests, TUF versions and root bytes commitment, not production keys or a durable copy of all remote metadata. Archive authentic source metadata externally for audit. There is no automatic transition from TUF withdrawal errors or removed delegation to a ledger event. Withdrawal/revocation are exercised using an explicit test-only local authority; authenticating a production control decision remains open. New signing roles, publisher legal identity, build provenance and actual release admission remain separate.

## Recovery and limitations
An external retained checkpoint can detect a missing/truncated prefix or conflicting prefix, even if a restored database is internally consistent. It must be provisioned independently from the database on recovery. Neither hash chain nor SQLite protects against privileged replacement of both database and checkpoint. Checkpoints are unsigned candidate evidence, not TUF snapshot versions or trusted timestamps. No automatic reset, backup restoration, durable external checkpoint store, distributed consensus, high availability, multi-host SQLite, online API, source/artifact archive or real publisher service. This is local transaction evidence only. Actual immutable production admission, legacy migration, concurrency between publication and signed snapshot generation, outbox/reconciliation, crash-safe authority/cache ownership, backup policy and production revocation signer must be reviewed separately.
